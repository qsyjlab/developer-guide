# 附件存储方案

---

## 一、目标

目标：

- 支持大文件分片上传
- 支持断点续传
- 支持相同文件引用复用
- 支持原文件、缩略图、预览产物分层存储

非目标：

- 不以文件名做去重
- 不在业务记录删除时直接删除物理文件

---

## 二、能力分层

### 2.1 上传层

- 初始化上传
- 分片上传
- 已上传分片查询
- 分片校验
- 上传完成确认

### 2.2 存储层

- 物理文件唯一存储
- 原文件与预览产物分离
- 内容哈希识别
- 上传状态管理

### 2.3 引用层

- 多业务对象引用同一物理文件
- 引用计数
- 逻辑删除与物理删除分离

---

## 三、推荐数据模型

建议拆成 4 张表。

### 3.1 文件主表

建议字段：

| 字段 | 说明 |
|------|------|
| `file_id` | 文件主键 |
| `content_hash` | 整文件哈希 |
| `file_size` | 文件大小 |
| `mime_type` | MIME 类型 |
| `ext` | 扩展名 |
| `storage_key` | 原文件存储键 |
| `storage_provider` | 存储提供方 |
| `upload_status` | 上传状态 |
| `preview_status` | 预览状态 |

### 3.2 上传会话表

建议字段：

| 字段 | 说明 |
|------|------|
| `session_id` | 上传会话 ID |
| `file_id` | 关联文件 |
| `chunk_size` | 分片大小 |
| `chunk_total` | 分片总数 |
| `uploaded_count` | 已上传分片数 |
| `status` | 会话状态 |
| `expire_at` | 会话过期时间 |

### 3.3 分片表

建议字段：

| 字段 | 说明 |
|------|------|
| `chunk_id` | 分片记录 ID |
| `session_id` | 所属上传会话 |
| `chunk_index` | 分片序号 |
| `chunk_hash` | 分片哈希 |
| `chunk_size` | 分片大小 |
| `storage_key` | 分片存储键 |
| `status` | 分片状态 |

### 3.4 文件引用表

建议字段：

| 字段 | 说明 |
|------|------|
| `ref_id` | 引用记录 ID |
| `file_id` | 关联文件 |
| `biz_type` | 业务类型 |
| `biz_id` | 业务主键 |
| `field_code` | 业务字段 |
| `status` | 引用状态 |

---

## 四、上传流程

### 4.1 初始化上传

输入：

- 文件名
- 文件大小
- MIME
- 整文件哈希
- 分片大小
- 分片总数

处理：

1. 查询是否存在相同 `content_hash`
2. 已存在时进入秒传 / 引用复用逻辑
3. 不存在时创建文件记录和上传会话

### 4.2 分片上传

输入：

- `session_id`
- `chunk_index`
- `chunk_hash`
- 分片二进制

处理：

1. 校验会话状态
2. 校验分片序号
3. 校验分片哈希
4. 写入分片存储
5. 更新分片记录

### 4.3 查询已上传分片

用途：

- 断点续传
- 页面刷新恢复上传
- 客户端重试时跳过已完成分片

返回：

- 已上传分片序号列表
- 当前会话状态

### 4.4 上传完成确认

处理：

1. 校验分片是否齐全
2. 合并分片
3. 校验整文件哈希
4. 写入原文件存储键
5. 标记文件状态为完成

---

## 五、断点续传方案

核心要求：

- 上传会话独立存在
- 分片状态可查询
- 客户端可跳过已成功分片

推荐规则：

| 项目 | 规则 |
|------|------|
| 会话标识 | 服务端生成 `session_id` |
| 分片大小 | 固定大小，避免客户端频繁变化 |
| 重试策略 | 单分片失败可重试 |
| 会话过期 | 长时间未继续上传则失效 |
| 恢复机制 | 前端根据 `session_id` 查询已完成分片 |

闭坑点：

- 不能只靠前端内存记录上传进度
- 不能只记录“上传成功”，不记录具体分片
- 合并前必须重新校验整文件哈希

---

## 六、文件去重与引用复用

### 6.1 去重规则

物理文件唯一性建议基于：

- `content_hash`

不要基于：

- 文件名
- 上传时间
- 业务对象 ID

### 6.2 相同文件复用

处理规则：

1. 上传前计算整文件哈希
2. 服务端查询是否已存在相同文件
3. 已存在时不再重复存储物理文件
4. 新增一条文件引用记录

### 6.3 引用复用场景

| 场景 | 处理 |
|------|------|
| 同一文件被多个业务对象上传 | 复用物理文件 |
| 同一业务对象多次选择同一文件 | 复用物理文件 |
| 不同模块引用同一文件 | 新增引用记录，不新增物理文件 |

---

## 七、删除策略

删除分两层：

### 7.1 业务删除

处理：

- 删除引用记录
- 不直接删除物理文件

### 7.2 物理删除

条件：

- 文件引用数为 0
- 不存在有效业务引用
- 预览产物可同步清理

建议：

- 走异步回收任务
- 不在业务请求链路中同步删对象存储

闭坑点：

- 删除业务记录时直接删物理文件
- 没有引用表，导致无法判断是否还能删
- 原文件删了，预览产物还残留

---

## 八、存储分层

建议至少分成 3 类对象：

| 类型 | 说明 |
|------|------|
| 原文件 | 上传的原始附件 |
| 缩略图 | 图片首帧、封面、小图 |
| 预览产物 | PDF、HTML、提取文本等 |

建议路径独立：

| 类型 | 路径示例 |
|------|----------|
| 原文件 | `origin/yyyy/mm/...` |
| 分片 | `chunk/yyyy/mm/...` |
| 缩略图 | `thumb/yyyy/mm/...` |
| 预览产物 | `preview/yyyy/mm/...` |

---

## 九、权限控制

不要直接暴露对象存储真实路径。

建议：

- 下载走服务端受控接口
- 私有文件使用短期访问地址
- 预览产物与原文件同样受权限校验
- 业务系统通过引用关系判断访问权限

---

## 十、失败与恢复

### 10.1 上传失败

处理：

- 保留会话状态
- 前端支持重试
- 查询已上传分片后继续

### 10.2 合并失败

处理：

- 记录失败原因
- 不标记文件完成
- 保留分片供重试或重建

### 10.3 会话过期

处理：

- 拒绝继续写入
- 要求重新初始化上传会话

---

## 十一、推荐接口

建议至少包含：

- `POST /attachments/upload/init`
- `POST /attachments/upload/chunk`
- `GET /attachments/upload/session/:id`
- `POST /attachments/upload/complete`
- `POST /attachments/reference/create`
- `POST /attachments/reference/delete`

---

## 十二、闭坑点

- 只按文件名判断是否重复
- 没有上传会话表
- 没有分片表
- 没有文件引用表
- 上传成功后不做整文件哈希校验
- 删除业务记录时直接删物理文件
- 原文件和预览产物混放
- 直接暴露真实对象存储路径
